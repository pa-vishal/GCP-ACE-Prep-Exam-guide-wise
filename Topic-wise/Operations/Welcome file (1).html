Operations Suite — ACE Mental Model (Deep, Practical)

🧠 Core Mental Model (read once)

Logs tell you what happened.
Metrics tell you how healthy things are.
Alerts tell you when to wake up.
Traces tell you where time is spent.

Almost every ACE ops question maps to one of these four.

What’s in the Operations Suite (names ACE expects)

  • Cloud Logging → logs
  • Cloud Monitoring → metrics, dashboards, alerts
  • Cloud Trace → request latency
  • Cloud Profiler → CPU/memory hotspots
  • Error Reporting → aggregated app errors

You don’t need internals — you need when to use which.

1️⃣ Cloud Logging (FIRST place you look)

What Logging answers

  • Why did this request fail?
  • What error occurred?
  • What did the app say?

ACE-safe usage

  • Use Log Explorer

  • Filter by:

    • Resource (VM, Cloud Run, GKE)
    • Severity (ERROR)
    • Time window

🧠 Rule: Errors → Logs first.

Very common ACE trap ⚠️

They’ll suggest:

  • Increase quota ❌
  • Check IAM ❌
  • Create alert ❌

If the app is already failing:
👉 Look at logs first.

2️⃣ Cloud Monitoring (health & trends)

What Monitoring answers

  • Is CPU too high?
  • Is memory exhausted?
  • Is latency increasing?
  • Is the service up?

Monitoring works with metrics, not logs.

Common ACE metrics

  • CPU utilization
  • Memory usage
  • Request count / latency
  • Error rate (derived metric)

🧠 Rule: Health & performance → Monitoring.

3️⃣ Alerts (notifications, not diagnosis)

What alerts do

  • Notify you when a metric crosses a threshold
  • Based on Cloud Monitoring

Examples:

  • CPU > 80%
  • Error rate > 5%
  • VM down

⚠️ Alerts do NOT fix anything. They only notify.

🧠 Rule: Alerts come after you understand the metric.

4️⃣ Logs → Metrics → Alerts (critical flow)

This flow is very exam-important:

Logs (raw events)
   ↓
Log-based metrics
   ↓
Monitoring alerts

ACE often asks:

“Create an alert when a specific log message appears”

Correct reasoning:

  • Create log-based metric
  • Create alert on that metric

5️⃣ Cloud Trace (latency questions)

What Trace answers

  • Which service is slow?
  • Where is time being spent?

ACE only tests recognition:

  • “Investigate request latency” → Cloud Trace

6️⃣ Error Reporting (app-level errors)

What it does

  • Groups exceptions (e.g., stack traces)
  • Tracks new vs recurring errors

ACE pattern:

“Track application errors over time” → Error Reporting

7️⃣ Ops Agent (Compute Engine & GKE)

What Ops Agent does

  • Collects:

    • Logs
    • Metrics

  • Replaces legacy agents

ACE scenario:

“VM metrics/logs not visible”
👉 Install Ops Agent

🧠 Rule: No data → check agent.

Operations Suite — Unified ACE Decision Table

Situation First Service
500 errors Cloud Logging (Log Explorer)
High CPU / memory Cloud Monitoring
Need notification Monitoring Alert
Slow requests Cloud Trace
App exceptions Error Reporting
No VM metrics Ops Agent
Alert on log pattern Log-based metric → Alert

If you follow this table, you won’t miss ops questions.

Operations Suite — ACE Mental Model (One-Page Summary)

🧠 Core Mental Model

Operations is about visibility, not fixing.
You observe, then act elsewhere.

Every ops question answers one of these:

  • What happened?
  • Is it healthy?
  • When should I be notified?
  • Where is it slow?

1️⃣ Cloud Logging — What happened?

Use when:

  • App errors (4xx / 5xx)
  • Crashes
  • Unexpected behavior

Key tool:

  • Log Explorer

Key ACE facts:

  • Logs are raw events

  • Filter by:

    • Resource
    • Severity
    • Time

🧠 Rule: Errors → Logging first.

2️⃣ Cloud Monitoring — Is it healthy?

Use when:

  • CPU / memory issues
  • Latency trends
  • Throughput
  • Availability

Key objects:

  • Metrics
  • Dashboards
  • Alerting policies

🧠 Rule: Health & performance → Monitoring.

3️⃣ Alerts — When should I wake up?

Key facts:

  • Alerts are based on metrics
  • Alerts notify only
  • Alerts do not fix problems

Common triggers:

  • CPU > threshold
  • Error rate > threshold
  • Resource unavailable

🧠 Rule: Alerts notify, they don’t diagnose.

4️⃣ Logs → Metrics → Alerts (VERY testable)

Logs
  ↓
Log-based metrics
  ↓
Monitoring alerts

ACE scenario:

“Alert when a specific error appears in logs”

Correct solution:

  1. Create log-based metric
  2. Create alert on that metric

5️⃣ Cloud Trace — Where is it slow?

Use when:

  • Request latency
  • Distributed services
  • Performance bottlenecks

🧠 Rule: Latency questions → Trace.

6️⃣ Error Reporting — What errors keep happening?

Use when:

  • Track recurring exceptions
  • Group stack traces
  • Identify new vs old errors

🧠 Rule: App exceptions over time → Error Reporting.

7️⃣ Ops Agent — Why is there no data?

Use when:

  • VM metrics missing
  • Logs not showing up

🧠 Rule: No VM data → check Ops Agent.

🔑 Operations Suite — Exam-Safe One-Liners

  • “500 errors” → Cloud Logging
  • “High CPU” → Cloud Monitoring
  • “Get notified” → Alerting
  • “Alert on log pattern” → Log-based metric
  • “Slow requests” → Cloud Trace
  • “No VM metrics” → Ops Agent

If you memorize just these, you’ll pass ops questions.
