Compute Engine (GCE) — Deep, Operational ACE Coverage

Compute Engine — ACE Depth Anchor

“On ACE, you own the VM’s full lifecycle: cost, deployment, access, operations, and recovery.”

GCE Lifecycle (how ACE thinks)

We will follow this order strictly:

  1. Set up solution environment
  2. Plan & configure VM
  3. Deploy & connect
  4. Operate & recover
  5. Secure access

🟦 Step 1: Set Up Solution Environment (Depth)

ACE-critical facts

  • Compute Engine is controlled by:

    • Project
    • Region / Zone
    • Quotas

  • You cannot create VMs if:

    • CPU quota is exceeded
    • API is disabled

What must be true before creating a VM

1️⃣ Compute Engine API enabled
2️⃣ Sufficient CPU quota in the region
3️⃣ Project linked to billing

If any of these fail → VM creation fails.

Very common ACE trap ⚠️

Scenario:

“VM creation fails with insufficient resources”
Check regional CPU quota

One-line memory hook 🧠

“No quota, no VM — regardless of money.”

Step 2: Plan & Configure the VM (REAL depth starts here)

1️⃣ Machine Types (ACE depth boundary)

What machine type controls

  • vCPU count
  • Memory
  • Most of the cost

ACE-relevant machine families (don’t overlearn)

Family When ACE expects it
E2 Default, cost-efficient workloads
N2 Higher performance
Custom When fixed shapes don’t fit
Spot (Preemptible) Cheap, fault-tolerant jobs

If the question says “cost-effective” → E2
If it says “unreliable but cheap” → Spot VM

Spot / Preemptible VMs (very testable)

Key properties

  • Can be terminated anytime

  • Max runtime:

    • Preemptible: 24 hours
    • Spot: no hard limit, but still interruptible

  • Much cheaper

When ACE expects Spot VMs

  • Batch jobs
  • Non-critical workloads
  • Fault-tolerant processing

One-line memory hook 🧠

“If it can die, make it Spot.”

2️⃣ Disks (second biggest cost driver)

Disk types ACE cares about

Disk Use case
Standard PD Cheap, low IOPS
Balanced PD General purpose
SSD PD High IOPS
Local SSD Ultra-fast, ephemeral

Very important ACE rule ⚠️

Local SSD data is lost when the VM stops.

ACE loves this trap.

Disk size & cost (exam logic)

  • You pay for:

    • Provisioned disk size
    • Not actual usage

  • Larger disk = higher cost even if empty

One-line memory hook 🧠

“Disks are billed by size, not fullness.”

Guided depth check (important)

Scenario:

You need a cheap VM for a batch processing job that:

  • Can be interrupted
  • Does not need persistent local data

👉 Which two Compute Engine features should you choose?

Answer with two short phrases.
✅ — Spot VM + Local SSD.

  • Spot VM
    → Cheapest compute
    → Accepts interruption
    → Ideal for batch / fault-tolerant jobs

  • Local SSD
    → Very fast
    → Ephemeral (data loss acceptable)
    → No need for persistence

This combination screams:
“Cheap, disposable compute.”

Common ACE trap ⚠️

They’ll try to tempt you with:

  • SSD Persistent Disk ❌ (unnecessary cost)
  • Regular VM ❌ (wastes money)
  • Snapshots ❌ (not needed for ephemeral jobs)

One-line memory hook 🧠

“Batch + disposable = Spot VM + Local SSD.”

Compute Engine — Step 4: Access & Security (VERY testable)

  • SSH access

SSH access — two models (must know)

1️⃣ SSH keys in metadata (legacy)

  • Keys stored in:

    • Project metadata
    • Instance metadata

  • Harder to manage at scale

2️⃣ OS Login (ACE-preferred)

  • Uses IAM for SSH access
  • Centralized
  • Auditable
  • Scales well

If the question mentions security, auditability, or central control → OS Login.

What OS Login does

  • Maps:
    • IAM user → Linux user
  • Controls:
    • Who can SSH
  • Uses IAM roles:**
    • compute.osLogin
    • compute.osAdminLogin

One-line memory hook 🧠

“Modern SSH on GCP = OS Login.”

OS Login roles (must memorize)

Role What it allows
roles/compute.osLogin SSH without sudo
roles/compute.osAdminLogin SSH with sudo (root)

1️⃣ Snapshots & Disk Resizing (Operational Reality)

Snapshots (quick recap)

  • Disk-level backups

  • Incremental

  • Used for:

    • Backup
    • Restore
    • Migration

Disk resizing (very testable)

Persistent disks can be resized while attached.

Key points:

  • You can increase disk size
  • You cannot decrease disk size
  • OS filesystem may need resize

One-line memory hook 🧠

“Disks only grow, never shrink.”

2️⃣ Managed Instance Groups (MIGs) — huge ACE topic

What a MIG is

A group of identical VMs created from an instance template.

MIGs provide:

  • High availability
  • Autoscaling
  • Auto-healing
  • Rolling updates

Instance Template (must know)

An instance template defines:

  • Machine type
  • Disk image
  • Startup script
  • Service account

Templates are:

  • Immutable
  • If you change config → create new template

One-line memory hook 🧠

“MIGs don’t change VMs — they replace them.”

Very common ACE scenario

“Ensure VMs are automatically recreated if they crash”

Correct answer:

Use a Managed Instance Group with auto-healing

3️⃣ Autoscaling (ACE scope)

MIGs can scale based on:

  • CPU utilization
  • Load balancer traffic
  • Custom metrics (advanced)

ACE usually focuses on:

  • CPU-based autoscaling

Guided depth check (important)

Scenario:

You need to:

  • Run identical VMs
  • Automatically replace failed VMs
  • Scale based on CPU usage
