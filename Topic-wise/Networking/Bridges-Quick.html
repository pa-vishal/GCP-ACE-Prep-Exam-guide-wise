Below is a clear, no-nonsense explanation of VPC Peering and Private Service Access (PSA), written the way senior cloud/network engineers explain it—plus why they are different and when to use which.

1️⃣ VPC Peering — Private connection between two customer VPCs

What it is

VPC Peering creates a private, RFC1918 IP-based connection between two separate VPC networks.

  • Both VPCs are customer-owned
  • No traffic goes over the public internet
  • Uses Google’s internal backbone

Key properties

Aspect VPC Peering
Connects VPC ↔ VPC
Ownership Both VPCs are customer-managed
IPs Private IP only
Firewall rules Still enforced separately in each VPC
Transitivity ❌ Not transitive
Typical use Mergers, acquisitions, shared services

Example (Ford scenario)

Ford acquires a smaller company that already has its own GCP VPC.
They peer the two VPCs so apps can communicate privately without merging networks or IAM.

Important limitations (this is where people mess up)

  • ❌ No overlapping CIDR ranges
  • ❌ No transitive routing
  • ❌ No central firewall enforcement across VPCs
  • ❌ Doesn’t work for Google-managed services (Cloud SQL, etc.)

👉 VPC Peering is lateral, between equals.

2️⃣ Private Service Access (PSA) — Private connection to Google-managed services

What it is

Private Service Access (PSA) is a specialized form of VPC peering between:

  • Your VPC
  • A Google-managed service VPC (not visible to you)

This is how Cloud SQL, Memorystore, Filestore get private IPs.

Key properties

Aspect PSA
Connects Customer VPC ↔ Google-managed service VPC
Ownership One side is Google-owned
IPs Private IP for managed services
Routing Controlled by Google
Firewall rules Apply on customer VPC side
Typical use Cloud SQL private IP

Example (your architecture)

Cloud Run → Cloud SQL
Traffic flows privately through Shared VPC → PSA → Google-managed Cloud SQL project
No public IPs. No internet exposure.

Why PSA exists (critical insight)

Google does not place managed services inside your VPC.

Instead:

  • They live in Google-owned service projects
  • PSA creates a controlled private bridge
  • You never see or manage the service VPC

👉 PSA is vertical, customer → Google service.

3️⃣ Side-by-side comparison (memorize this)

Feature VPC Peering Private Service Access
Connects Customer VPC ↔ Customer VPC Customer VPC ↔ Google-managed service
Purpose Org-to-org or project-to-project Access managed services privately
Google-managed side ❌ No ✅ Yes
Can connect Cloud SQL ❌ No ✅ Yes
CIDR planning required ✅ Yes ✅ Yes
Seen in enterprise Acquisitions, shared platforms Databases, caches, file services

4️⃣ How this fits your Shared VPC design

Service Projects
      │
      ▼
Host Project (Shared VPC)
      │
      ├── VPC Peering → Another company / legacy VPC
      │
      └── PSA → Google-managed Cloud SQL

Why this is powerful

  • Central network team controls routing + security
  • App teams get private access without complexity
  • Google services stay isolated and hardened

5️⃣ Interview-grade explanation (30 seconds)

“VPC Peering connects two customer-owned VPCs privately and is typically used for mergers or shared platforms.
Private Service Access is a specialized peering that connects our VPC to Google-managed services like Cloud SQL, enabling private IP access.
In Shared VPC, both are anchored at the Host Project to maintain centralized control.”

If you can say that confidently → you pass.

6️⃣ Common mistakes to avoid (very important)

  • ❌ Thinking PSA is just “another VPC peering”
  • ❌ Trying to peer directly to Cloud SQL
  • ❌ Overlapping CIDRs
  • ❌ Expecting firewall rules to propagate across VPCs
